# 第一阶段规格：模型库 + 地物识别

状态：待实现  
日期：2026-10-19  
关联：GitHub Issue #53

## Problem Statement

模型库中的地物识别模型来自多个项目，依赖的 Python、PyTorch、CUDA 和第三方库不同。直接把模型代码导入 FastAPI 会造成依赖冲突，也会扩大 Web 后端执行模型代码的权限范围。现有大图脚本还重复实现 GeoTIFF 读取、切片、拼接和写出，导致空间元数据、无效数据和重叠区域融合不一致。

当前模型库需要从空目录重新建立。第一阶段要支持地物识别模型的登记、验证、运行和结果复用，同时允许管理员提前登记变化检测模型，以便模型库能容纳两类模型。变化检测模型在本阶段只做基础运行检验和目录管理，不进入任何变化检测业务页面。

## Solution

建立由 Web 后端、构建 Worker、推理 Worker 和临时容器组成的模型运行架构。

模型库由数据驱动，支持两种模型类型：地物识别模型和变化检测模型。管理员负责上传、编辑、重新验证和下线；普通用户可以查看模型库和公开状态摘要，但不能修改模型资产，也不能下载代码或权重。模型数量不在代码中固定，初始导入数量和后续新增数量均由目录数据决定。

一个模型版本以版本化模型包为上传单位，模型代码、权重、配置和依赖元数据按内容哈希保存。构建 Worker 负责安全解析模型包、构建或复用运行环境镜像并执行基础运行检验。推理 Worker 负责队列、GPU 分配、临时容器和任务状态。Web 后端不直接导入模型依赖，也不直接操作 Docker。

容器内的 `rs_runner` 统一负责 GeoTIFF 读取、波段处理、切片、尺寸补齐、批量推理、重叠块概率融合、空间元数据传递和掩膜 GeoTIFF 写出。模型适配器只实现 `load()` 和 `predict(batch)`，返回含类别维度的浮点概率张量。

第一阶段只有地物识别页面可以执行地物识别模型。地物识别结果遵循 `land-cover-6/v1`，保存分类掩膜、六类面积、影像和生产模型版本，并支持符合完整身份的结果复用。

## User Stories

1. 作为管理员，我想从空模型库导入地物识别模型版本，以便建立可用的模型目录。
2. 作为管理员，我想导入变化检测模型并完成基础运行检验，以便提前维护未来业务需要的模型。
3. 作为管理员，我想看到上传、构建、验证和失败阶段，以便定位模型包问题。
4. 作为管理员，我想在模型资产不变时重新触发验证，以便恢复临时环境或 Worker 故障造成的失败。
5. 作为管理员，我想修改模型描述、标签等目录信息，以便维护用户可读的模型说明。
6. 作为管理员，我想用新权重、代码、manifest 或推理参数创建新版本，以便模型版本不可变且可追溯。
7. 作为管理员，我想下线旧生产版本，以便新的生产版本进入业务选择器，同时保留历史结果所需的资产。
8. 作为普通用户，我想查看模型库中的地物识别模型和变化检测模型，以便了解系统当前维护的模型。
9. 作为普通用户，我想看到模型类型、版本、状态、输入说明和基本资源信息，以便选择合适的模型。
10. 作为普通用户，我想只能在地物识别页面选择地物识别模型，以便不会把变化检测模型用于分类任务。
11. 作为普通用户，我想看见技术可用但暂时没有业务入口的变化检测模型，以便知道它已经登记但当前不可调用。
12. 作为普通用户，我想提交影像进行地物识别，以便获得六类分类结果和面积统计。
13. 作为普通用户，我想在重复使用同一影像和同一生产模型时复用已有结果，以便避免重复推理。
14. 作为普通用户，我想查看地物识别历史、分类图、面积和模型版本，以便复核过去的分析。
15. 作为普通用户，我不能上传、编辑、重新验证、下线或删除模型，以便模型目录保持受控。
16. 作为普通用户，我不能下载模型代码、权重、依赖文件或完整构建日志，以便模型资产不被当作公开下载内容。
17. 作为模型适配器开发者，我想只实现模型加载和批量前向，以便不重复实现 GeoTIFF I/O、切片和整图拼接。
18. 作为运维人员，我想让每张 GPU 首版同时只执行一个任务，以便控制显存竞争。
19. 作为运维人员，我想让推理容器以非 root、默认禁网和只读模型挂载运行，以便降低模型代码的运行风险。
20. 作为维护者，我想让模型目录和页面按模型数据动态生成，以便后续增加模型时无需修改固定枚举。

## Implementation Decisions

### 模型类型与阶段边界

- 模型库支持 `land-cover`（地物识别模型）和 `change-detection`（变化检测模型）两类模型；目录数量由数据库记录决定，不在前端或后端固定为某个数量。
- 第一阶段完整交付地物识别运行链路：模型目录、模型包、容器运行、分类结果、六类面积、历史和复用。
- 变化检测模型在第一阶段可以上传、构建、基础验证、展示和维护，但不能被地物识别页面或任何变化检测页面选择。
- 变化检测模型的双影像业务输入、变化类别语义、变化面积、结果图、历史和报告属于第二个独立 spec。
- 技术可用和业务可调用是两个独立判断：模型通过基础运行检验后可标记为技术可用；页面是否可选择由模型类型和当前业务入口能力决定。

### 模型包、版本和资产

- 一个压缩包是一个模型版本的上传单位，包含 `manifest.yml`、依赖描述、统一入口源码、生产权重和必要配置。
- 模型包不包含训练数据、训练日志、开发工具目录、缓存和不参与推理的重复检查点。
- 解包拒绝路径穿越、绝对路径、逃逸符号链接、压缩炸弹、超出文件数/总大小限制和不允许的文件类型。
- manifest 至少声明模型类型、模型版本、入口、输入类型、类别表/输出契约、输入波段、数据类型与归一化、`tile_size`、`overlap`、`size_divisor`、批量大小、框架/CUDA 约束、CPU/内存/GPU 需求和运行输出约定。
- 修改模型代码、权重、manifest、依赖、入口或推理参数时创建新模型版本；修改名称、描述、标签等目录信息可以更新元数据而不改变版本身份。
- 普通用户选择逻辑模型，不直接选择版本；系统使用该逻辑模型唯一的生产版本。管理员验证新版本后可切换生产版本，旧版本不再进入业务选择器。
- 版本身份由模型版本号、环境镜像摘要、代码/配置内容哈希和权重哈希共同组成。识别结果必须绑定完整版本身份。
- 首版使用本机文件存储，存储接口保留迁移到 MinIO 或 S3 的能力。

### 权限与目录可见性

- 普通用户对模型库只读，可查看模型名称、类型、描述、公开状态、输入说明、可用业务能力和基本资源信息。
- 管理员可上传、编辑目录信息、触发重新验证、切换生产版本和下线版本。
- 普通用户不能上传、编辑、重新验证、下线或删除模型，也不能下载模型代码、权重、依赖文件、内部路径或完整构建/验证日志。
- 构建日志、验证诊断、失败堆栈摘要、镜像摘要和资产哈希只对管理员可见。
- 物理删除不作为模型生命周期操作；下线版本在仍被历史结果引用时必须保留。

### 生命周期与基础运行检验

- 模型状态包括上传中、构建中、验证中、可用、构建失败、验证失败和已下线。
- 模型进入“可用”只要求基础运行检验通过，不设置单独的效果评估状态。
- 地物识别模型的基础检验使用平台生成的单幅合成 GeoTIFF；变化检测模型的基础检验使用两幅空间参考一致的合成 GeoTIFF。
- 基础检验包括模型包和 manifest 校验、入口导入、权重加载、适配器输入输出形状、类别/数据类型、空间元数据、资源限制、超时和退出行为。
- 真实影像或标注数据上的效果由模型提供者在导入前负责确认，不作为模型进入目录的前置条件。
- 验证失败版本保留诊断信息；管理员可在资产未变时重试验证。资产或推理契约发生变化时创建新版本。
- 模型按版本独立验证和上线，不要求等待全部地物识别模型或变化检测模型完成。

### 统一推理协议与 `rs_runner`

- `load()` 在容器启动阶段加载模型和权重；加载失败必须使任务进入可诊断的失败状态。
- `predict(batch)` 接收已预处理的 tile，返回形状包含批次、类别、高度、宽度的浮点概率张量；不能只返回最终 `argmax` 标签。
- 地物识别模型的输出必须匹配 `land-cover-6/v1`；内部类别顺序不同必须提供明确映射，无法映射的模型不能进入地物识别可调用目录。
- 适配器负责网络结构、权重加载、块内归一化和模型特有后处理，不负责 GeoTIFF 文件访问、宿主机路径查找或整图拼接。
- `rs_runner` 负责读取 GeoTIFF、保留 CRS/transform/尺寸/有效掩膜、波段选择、切片、边缘补齐、尺寸对齐、批量调度、重叠概率融合和掩膜 GeoTIFF 写出。
- 重叠 tile 使用确定性的 Hann 窗或 manifest 声明的等价权重融合；概率在整图融合后才转换为类别标签。
- nodata 和未覆盖区域保持独立有效性语义，不作为有效像素的“其他／背景”。采用条带或分块累积，避免整图概率张量占满显存。

### 构建 Worker、推理 Worker 与资源安全

- Web 后端不直接导入模型依赖、不在请求线程中操作 Docker、不动态创建或切换 Conda 环境。
- 构建 Worker 负责安全解包、manifest 校验、镜像构建或复用、入口检查、权重加载和基础运行检验。
- 推理 Worker 负责队列消费、GPU 分配、临时容器生命周期、进度采集、结果落盘和失败归因。
- 每张 GPU 首版同时执行一个任务；没有可用 GPU 时任务排队。
- 推理容器默认以非 root 运行，模型资产只读挂载，默认禁用网络，并限制 CPU、内存、共享内存、进程数、写入目录和 GPU。
- 构建容器和推理容器分离；构建阶段只访问配置好的内部依赖源，推理阶段不继承构建网络权限。
- 任务超时、OOM、非零退出、输出缺失、类别越界或空间元数据不一致时，Worker 必须回收容器并记录结构化失败原因。
- 输出使用临时文件加原子提交，避免失败任务留下可复用的半成品。

### 地物识别业务行为

- 地物识别页面只展示模型类型为 `land-cover` 且当前生产版本可调用的模型。
- 用户提交影像和逻辑模型后，系统解析当前生产版本并创建异步推理任务；前端只依赖任务状态和结果引用，不感知 Docker 或容器路径。
- 单期识别结果包括分类掩膜、影像身份、逻辑模型、完整生产版本身份、六类面积、空间范围和计算时间。
- 结果复用条件包括同一影像、同一逻辑模型生产版本、相同输入契约、相同空间处理参数和完整输出资产；条件不匹配时重新推理。
- 单期面积统计覆盖影像有效数据范围；无效数据不被计入“其他／背景”。
- 普通用户可以查看识别历史和结果详情，但不能选择已下线或非生产版本重新执行。
- 模型更新不会改变历史识别结果；历史结果读取不重新推理。

### 测试接缝

最高测试接缝是“模型运行契约”：用受控的模型适配器和合成 GeoTIFF 验证包解析、`load()`/`predict(batch)`、`rs_runner`、容器任务和输出资产。业务层通过一个假的可控运行时验证模型筛选、任务状态、结果复用和历史查询，避免页面测试依赖真实 GPU 和具体模型网络。

## Testing Decisions

- 测试外部行为和模型运行契约，不测试具体 Docker 命令或网络实现细节。
- 模型包测试覆盖合法包、缺失 manifest、非法路径、符号链接、压缩大小/文件数超限、错误类别映射和错误资源字段。
- 基础验证测试覆盖地物识别单幅合成 GeoTIFF、变化检测成对合成 GeoTIFF、入口加载、权重加载、输出形状、类别/数据类型、CRS/transform、资源限制和重试。
- `rs_runner` 测试覆盖波段读取、切片、边缘补齐、重叠概率融合、nodata 传播、空间元数据保留、类别输出和原子提交。
- 适配器契约测试覆盖 `load()` 和 `predict(batch)` 的批次维度、类别维度、概率范围、映射和错误行为。
- Worker 集成测试覆盖上传、构建、验证、可用/失败状态、管理员重试和容器清理。
- 权限测试覆盖普通用户只读模型库、管理员写操作、资产下载禁止和管理员诊断信息可见性。
- 地物识别集成测试覆盖模型类型筛选、异步任务、结果保存、六类面积、结果复用、历史查询和生产版本切换。
- 变化检测模型在第一阶段只验证目录登记、基础运行检验和不可调用状态，不测试变化检测业务结果。

## Out of Scope

- 变化检测页面的任何业务执行能力。
- “识别完作差”和“直接变化检测”双模式。
- 变化检测模型的真实业务输出语义、变化类别、变化面积、历史和报告。
- 真实影像/标注数据上的自动效果评估、IoU/F1 门槛或效果评估状态。
- 任意用户上传训练项目并立即执行。
- Web 后端直接安装或导入模型深度学习依赖。
- 上传请求中动态创建或切换 Conda 环境。
- 首版同卡多任务显存估算并发、自动纠正影像偏移或自动配准。
- 删除仍被历史结果引用的模型版本资产。

## Further Notes

- 本规格基于 Issue #53 原规格收窄而来，保留 Docker 隔离、统一模型包、构建 Worker、推理 Worker、GPU 单任务和 `rs_runner` 决策。
- 变化检测模型目录和基础运行检验属于第一阶段的模型库能力；变化检测业务执行将在第二个独立 spec 中定义。
- 模型效果由模型提供者负责确认；系统基础检验只证明模型符合运行契约，不宣称模型效果质量。
- 本规格确认后，下一步才调用 `$to-tickets` 拆分实现任务。
